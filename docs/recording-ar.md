## Checkpoint 1 — الاختبارات (0:30–1:35)

```powershell
docker run --rm forjulia-tests pytest -v
```

«Checkpoint 1. هذه الاختبارات تعمل محلياً على جهازي داخل Docker. اختبار health يتأكد من تحميل الموديل ويقارن بصمته مع الملف. اختبار contract يتأكد من شكل الاستجابة وأن الاحتمال بين صفر وواحد. اختبارات schema ترفض القيم السالبة والحقول الناقصة والإضافية والأنواع والفئات الخطأ. عندنا edge case للأصفار ولرقم كبير جداً. اختبار deterministic يتأكد أن الطلب المعروف يرجع 0.895 كل مرة. واختبار إعادة التدريب يتأكد أن نفس البيانات ونفس seed يعطوا نفس التوقعات. إذا ملف الموديل مفقود، التطبيق يفشل عند البداية بدل ما يعلن أنه جاهز.»

اعرضي `src/train/train.py` سريعاً: فصل التدريب عن الـnotebook، تجهيز المتغيرات العددية والفئوية، LogisticRegression، وتقسيم stratified مع seed=42. لا تصفي نتائج الدقة بأنها مثالية؛ هذا نموذج تعليمي.

## Checkpoint 2 — Dockerfile والخدمة (1:35–3:45)

افتحي Dockerfile ومرّي على الأسطر بالترتيب:

«Checkpoint 2. أول FROM يحدد Python 3.12 وصورة مثبتة بـdigest، يعني محتوى محدد وليس tag متغير فقط. AS builder يسمي مرحلة البناء. WORKDIR يحدد مجلد العمل. RUN ينشئ virtual environment، وENV يجعل أدواته هي المستخدمة. COPY ينقل قائمة المكتبات المثبتة بإصدارات محددة، وبعدها pip يثبتها بدون cache. ننقل src والبيانات، ثم ندرب الموديل بنفس بيئة التشغيل.

مرحلة test تبدأ من builder. ننسخ متطلبات التطوير والإعدادات ونثبتها، ثم ننسخ الاختبارات والطلب التجريبي. RUN يشغل Ruff وpytest، ويفشل البناء إذا أي فحص فشل.

آخر FROM يبدأ runtime منفصل. ENV يمنع كتابة bytecode ويجعل logs تظهر مباشرة، ويحدد مسار البيئة. WORKDIR هو /app. ننشئ مستخدم ومجموعة رقم 10001. ننسخ البيئة والكود والموديل من builder، بدون أدوات الاختبار والبيانات. USER يمنع التشغيل كـroot. EXPOSE يوثق المنفذ 8000. HEALTHCHECK يطلب /health كل 15 ثانية؛ له timeout ومحاولات وفترة بدء. CMD يشغل Uvicorn داخل الحاوية على المنفذ 8000.»

```powershell
docker compose ps
docker compose exec api id
curl.exe http://localhost:8000/health
curl.exe -H "Content-Type: application/json" --data-binary "@sample_request.json" http://localhost:8000/predict
```

«الحاوية healthy والمستخدم 10001. health يعرض بصمة الموديل المحمل، وpredict يرجع احتمال ترك العميل للخدمة.»

## Checkpoint 3 — Pull request وCI وGHCR (3:45–5:15)

افتحي الـPR المدموج وتبويب Checks، ثم تشغيل CI على main.

«Checkpoint 3. التغيير دخل من فرع مستقل عبر Pull Request. job الأول يشغل lint والاختبارات. job الثاني يبني الصورة ويشغل Trivy ويجرب endpoints داخل الحاوية. كل action مستخدم مثبت بـcommit SHA كامل. Trivy يمنع النشر إذا وجد ثغرات HIGH أو CRITICAL لها إصلاح متاح؛ هذا لا يعني عدم وجود أي ثغرات أخرى. النشر إلى GHCR يحصل فقط بعد النجاح على main، والـtag هو commit SHA كامل.»

افتحي خطوة Trivy وأظهري نجاحها، ثم خطوة Publish والـjob summary حيث يظهر digest. افتحي Package في GitHub وأظهري الـSHA tag. اشرحي أن tag يربط الصورة بالـcommit، بينما digest يحدد محتوى الصورة.
